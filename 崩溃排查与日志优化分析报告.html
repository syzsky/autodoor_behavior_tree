一执行调用链还原：『启动树』节点究竟做了什么

『启动树』对应 bt_nodes/actions/start_tree.py 中的 StartTreeNode，逻辑核心是"启动另一棵已加载的行为树"，调用栈还原如下：

# 主树引擎线程（daemon 线程）
BehaviorTreeEngine._run_loop bt_core/engine.py:264
  └─ root_node.tick(context) engine.py:278（已有 try/except 兜底）
     └─ StartTreeNode._execute_action start_tree.py:25
        └─ tab_manager.start_tab(tab_id) gui_tab_manager.py:137
           └─ on_tab_start_request(已注册的 GUI 回调) gui_tab_manager.py:138
               └─ 启动目标子树 → 新的 daemon 引擎线程（engine.start → _run_loop）◆ 关键节点
关键点：『启动树』会启动一棵子树，从而创建第二条＋引擎 daemon 线程。子树线程内发生的任何异常都不在主线程 sys.excepthook 的覆盖范围内，也不在内层 engine._run_loop 的 try/except 内（该 try/except 只包裹当前线程的 tick，见 engine.py:275-315）。

同时，engine.start() 在每次启动时调用 LogManager.clear_run_log()，把 run_log.txt 清空为当次现场（log_manager.py:88、253-261）。因此崩溃发生时记录的运行现场，是"最后一次启动后的鼠标操作日志"，而非完整的节点流转轨迹。

二崩溃无日志的根因分析（证据链）

我按"异常/崩溃可能发生的位置 → 该位置是否有日志出口 → 出口是否真的落盘"推演，逐一核对了全部日志路径，发现以下结构性漏洞叠加共同导致崩溃"零输出"。

漏洞 ① 全程缺失线程级未捕获异常钩子（致命）

全项目检索 threading.excepthook / set_excepthook / faulthandler，无任何一处启用。只有两类主线程钩子：

  • main.py:24-36 的 setup_error_logging() → 仅注册 sys.excepthook（主线程）
  • bt_utils/crash_recovery.py:33-40 的 CrashRecoveryHandler.install() → 同样仅覆盖 sys.excepthook
行为树引擎运行在 daemon=True 线程中（engine.py:96）。Python 3 中，线程内未捕获异常走 threading.excepthook（默认打印到 stderr），不会触发 sys.excepthook。打包成 exe 后 sys.stderr 无处可去 → 引擎线程、子树线程、GUI 回调线程中的未捕获异常完全静默消失，正是"没有任何崩溃输出"的最直接解释。

漏洞 ② 引擎 try/except 覆盖范围有限

engine._run_loop 的 try/except（engine.py:277-315）只包裹 当前线程 的 root_node.tick()。而『启动树』打开的内层子树线程、on_tab_start_request 回调线程均在其外。一旦异常落在这些位置，即便有日志代码也不会执行。

漏洞 ③ 前端日志（成功/失败/异常）从不落盘

LogManager.log() 把 LogEntry 放入内存 buffer 并派发 UI 刷新（log_manager.py:299-315），不写入任何文件。debug_print 才写调试文件，run_log 只写鼠标/窗口操作。StartTreeNode 里大量使用的前端日志（log_success / log_failure / log_info / log_aborted）在界面正常时可见，但 GUI 一旦崩溃或退出，全部丢失，无文件可查。

漏洞 ④ 崩溃现场快照为空 / 信息不足

run_log 被清空且维度单一engine.start() 每次清空 run_log（log_manager.py:88、253-261）；run_log 仅记录 [MOUSE]/[CTX]/[WIN]，缺少节点流转轨迹（[EXEC] 已被移除） 崩溃恢复文件流于形式CrashRecoveryHandler 只在主线程异常时落 crash_*.json，线程级/进程级崩溃不会产生 无 faulthandlerC 扩展层（dd 输入、图像处理、pyautogui 后台）若 segfault 会直接终止进程，无任何栈 dump

证据佐证：两份日志确实"空有输出、不见崩溃"

日志规模内容构成关于崩溃的信息
debug_log 27330 行 [WARN] 移动文件到缓存失败 ×669、[DEBUG] 条件节点每 tick 失败、[DD] 鼠标操作 结尾常规运行，无任何 Traceback / ERROR
run_log 807 行 [MOUSE] ×438、[CTX] ×360、[WIN] ×9，全部为鼠标/坐标/点击细节 无异常，且定位不到"运行到哪个节点"

三根因结论与分级

等级结论置信度说明
确定性缺陷 线程级未捕获异常无任何钩子记录，exe 环境下 stderr 丢弃 → 崩溃"零日志"是必然，不是偶发 确凿（代码层面 100%） 无论崩溃点具体在哪棵线程里，当前体系都无法留痕
高可能性 崩溃触发点位于『启动树』内部的子树引擎 / GUI 回调 / 子树后续节点，不在内层 try/except 内 高（待复现取证） start_tab → on_tab_start_request 调用链为跨线程派发
中等可能性 GUI 主线程（tkinter mainloop）内的回调异常导致界面崩溃/退出 中 前端日志不落盘，GUI 一崩即丢
低可能性 C 扩展层 segfault（dd 输入 / 图像处理 / pyautogui 后台调用）直接终止进程 低 无法用 Python 日志捕获，需 faulthandler / minidump
最可能组合：『启动树』启动子树时，在进入内层引擎线程或 GUI 回调线程时抛出的异常，恰好落在所有日志出口之外，从而表现为"运行到启动树就崩、且日志零输出"。加入线程级钩子 + 前端日志落盘后可一步锁定真实异常点。

五增加崩溃 / 卡死日志记录的方案设计

5.1 方案总览（建议分三步落地）

优先级方案覆盖问题成本 / 侵入度
P0 · 必做 注册线程级异常钩子 + 前端日志落盘 崩溃"零输出"的根因 低 · 仅改 main.py / log_manager.py
P0 · 必做 启用 faulthandler 进程级 segfault / 卡死全线程栈 dump 极低 · 3 行代码
P1 · 建议 引擎线程心跳 / watchdog 卡死检测 卡死（界面无响应 / 引擎挂起） 中 · 改 engine.py + 新增守护线程
P1 · 建议 run_log 增加节点流转轨迹 现场无法定位到"哪个节点" 低 · 恢复精简版节点执行日志

5.2 实现要点

① 线程级异常钩子 —— 在 main.py 的 setup_error_logging() 内追加，统一把 所有 线程的未捕获异常写入 debug 文件：
import threading
def _thread_hook(args):
    tb = "".join(traceback.format_exception(
        args.exc_type, args.exc_value, args.exc_traceback))
    LogManager.debug_print("[THREAD-CRASH] thread=%r\n%s" % (args.thread.name, tb))

threading.excepthook = _thread_hook
# 可选：连主线程也统一走同一出口
② 前端日志落盘 —— 在 LogManager.log() 或 log_failure/log_info 中，把 FAILURE/ERROR 级 LogEntry 追加写入 debug 文件（保留 UI 派发逻辑不变），确保 GUI 崩溃后仍有文件记录节点失败/异常。成功后 true 的可仅落盘 INFO 摘要。
③ faulthandler —— 启动早期禁用缓冲并开启全线程栈 dump，卡死 / segfault / 主线程异常时输出到文件而非 stderr：
import faulthandler, sys, os
faulthandler.enable(os.open(os.path.join(LOG_DIR, "faulthandler.log"), os.O_WRONLY|os.O_CREAT), all_threads=True)
# all_threads=True 让卡死时能 dump 出引擎线程 / 子树线程的完整栈
④ 引擎线程心跳 / 卡死 watchdog —— 行为树引擎属常驻 tick 循环，天然适合心跳检测：
  • 在引擎的 _run_loop 每轮记录 self._last_tick_ts = time.time()（含线程 ID / 子树名）。
  • 新增守护线程，每 N 秒巡检所有引擎实例：若某引擎 tick_interval 间隔远超阈值（如 >10s）而未推进，判定疑似卡死，调用 faulthandler.dump_traceback_later() 或 faulthandler.dump_traceback 到文件，并输出 [WARN] 卡死告警。
  • 结合 MessageBus.request() 已有的死锁防护（message_bus.py:122-148）扩展超时告警。
⑤ run_log 补充节点流转 —— 前端日志不落盘是现场缺失主因；建议把"节点开始执行 / 返回状态"这一级精简流转追加写入 run_log（而非还原完整的 [EXEC] 细节），使崩溃时能定位到失败节点。

5.3 对 CrashRecoveryHandler 的补强建议

现有 crash_recovery.py 只处理主线程。在其 install() 中补注册 threading.excepthook，并在回调里保存 args.thread、引擎 round 编号；同时将崩溃快照的落盘目录由 data/recovery 统一并入项目 logs/，便于集中取证。

六落地优先级与实施建议

次序动作预期收益
①补线程级异常钩子 + 前端日志（FAILURE/INFO）落盘立即能抓到本次崩溃的完整 Traceback
②启用 faulthandler（all_threads=True，输出到 logs/）覆盖进程级崩溃与卡死栈 dump
③精简高冗余日志（缓存 WARN 去重限频、鼠标/点击过程合并、条件节点节流）日志体积下降 70%+，关键信息不再被淹没
④引擎心跳 watchdog + run_log 节点流转轨迹卡死有告警、崩溃可定位节点
建议尽快复现验证：先按 ①② 打上日志增强后，让用户复现一次"运行到启动树崩溃"，即可从 debug 文件/faulthandler.log 直接拿到精确异常栈，从而最终确认是子树引擎线程、GUI 回调线程还是 C 扩展层——无需再靠推测。
